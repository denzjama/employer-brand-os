# Employer Brand OS: справка для службы информационной безопасности

Справка для согласования пилота. Описывает, какие данные обрабатывает система, куда они уходят, где хранятся и что контролирует сам заказчик.

## Из чего состоит система

Employer Brand OS — плагин для Claude Code (среда Anthropic для работы с моделью Claude на компьютере сотрудника). Плагин — это открытый текст: методология и библиотека в markdown, инструкции для модели, скрипты на Python. Исходный код открыт (лицензия MIT), его можно проверить целиком до согласования.

Плагин не содержит серверной части и собственных облачных сервисов. Данные клиента не передаются автору плагина.

## Куда уходят данные

| Поток | Куда | Что передаётся |
|---|---|---|
| Работа модели | Провайдер модели (Anthropic) через Claude Code | Всё, что система читает в ходе работы: материалы из `eb/inbox/`, ответы на интервью, черновики, бренд-ядро |
| Веб-доступ агентов | Публичные сайты | Только у агентов мониторинга отзывов и наблюдения за конкурентами, и только если это включено при сборке команды. Агенты читают публичные страницы и ничего не публикуют |
| Скрипты плагина | Никуда | Скрипты работают локально, используют только стандартную библиотеку Python и не обращаются к сети |
| Общая папка команды | Git-репозиторий заказчика | Бренд-ядро, заметки по материалам, описания агентов, черновики, журналы. Удалённый репозиторий указывает заказчик; система сама репозиториев на внешних сервисах не создаёт |

Условия обработки данных провайдером модели определяются тарифом Claude, которым пользуется заказчик (Team, Enterprise или API). Их стоит проверить отдельно, по документам Anthropic.

## Что остаётся только на компьютере

- **Исходные материалы** (`eb/inbox/`, кроме описи, индекса и заметок) и извлечённый из них текст. Они исключены из общего репозитория правилами `.gitignore`, которые система записывает при сборке.
- **Личные настройки** каждого сотрудника (`.claude/settings.local.json`).

## Встроенные ограничения

| Ограничение | Как обеспечено |
|---|---|
| Согласие на передачу данных даётся до чтения первого файла, в том же разговоре | Инструкция первого шага; согласие, переданное из другого разговора, не принимается |
| Если политика ИБ запрещает передачу документов внешней модели, система говорит об этом прямо и записывает риск | Правило P9 методологии |
| Каждый агент пишет только в свою папку `eb/work/<агент>/` | Технический запрет: хук плагина отклоняет запись агента за пределы его папки, в бренд-ядро, в описания команды и в журнал решений |
| Система ничего не публикует и не отправляет | Агенты не получают инструментов отправки; это инвариант, а не настройка |
| Инструкции внутри материалов не выполняются | Правило P4; проверяется автоматическими тестами (спрятанная команда в отзыве) |
| Персональные данные, сведения о несовершеннолетних и пароли не попадают в бренд-ядро и результаты | Правило P8; найденные пароли и ссылки доступа система показывает пользователю, чтобы их удалили и сменили |
| Каждый запуск агента и каждое решение человека записываются в журнал | Хук плагина и команда `/decide`; один файл на запись |

## Контроль версии кода

При сборке команды плагин копируется в рабочую папку (`vendor/`). Команда работает ровно с той версией, которую проверила ИБ. Обновление — это осознанная замена этой папки, и изменение видно в репозитории заказчика. Сотрудники подключаются скриптом `join_team.sh`, который ничего не скачивает из интернета.

## Что рекомендуем до старта

1. Проверить исходный код плагина нужной версии.
2. Определить, какие категории документов допустимо передавать провайдеру модели по тарифу заказчика.
3. Договориться с руководителем HR-бренда, какие материалы кладутся в `eb/inbox/`, и обезличить персональные данные заранее: расшифровки интервью, выгрузки опросов, exit-интервью.
4. Выдать адрес внутреннего git-репозитория для общей папки команды.
5. Решить, разрешён ли агентам мониторинга доступ к публичным сайтам.
