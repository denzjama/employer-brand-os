# Employer Brand OS — архитектура

Мультиагентная система для функции Employer Brand. Подключается к Claude Code одним плагином, проводит диагностику функции, собирает под неё команду агентов и со временем перестраивает её по тому, как команда реально работает.

Продолжение [Employer Brand Auditor](https://github.com/denzjama/employer-brand-auditor): правила доказательности и аудит текстов становятся контролем качества для всего, что агенты готовят наружу.

## 1. Проблема и позиционирование

Руководитель HR-бренда не понимает, куда и как встраивать AI: какие процессы отдать, как не потерять качество и голос бренда, как преодолеть сопротивление команды и как превратить разовые эксперименты в постоянную практику.

Поэтому продукт — **операционная модель функции с агентами внутри**, а не набор агентов:

- какие процессы отдать агентам, какие усилить, какие оставить людям;
- у каждого агента есть человек-владелец;
- каждый агент встроен в ритуал команды (планёрка, ревью, отчёт);
- система сама предлагает, что поменять, а люди решают.

**Покупатель:** CHRO. **Пользователь:** руководитель и менеджеры EB. **Модель:** SaaS-консалтинг — технология плюс сопровождение внедрения. **Рынок:** Россия и СНГ, позже глобальный.

## 2. Четыре фазы

```
 1. ДИАГНОЗ ──► 2. СБОРКА ──► 3. РАБОТА ──► 4. АДАПТАЦИЯ
     ▲                                          │
     └──────────── повторная диагностика ◄──────┘
```

### Фаза 1. Диагноз функции

**Вход:** материалы о команде (структура, задачи, планы, результаты, стратегии, EVP) и интервью с руководителем.

**Принцип:** сначала читаем, потом спрашиваем. Система разбирает материалы, строит гипотезы и спрашивает только то, чего в материалах нет. Время руководителя — самый дорогой ресурс.

**Что происходит:**
1. Материалы раскладываются и индексируются, с пометками о чувствительных данных.
2. Из материалов собирается **бренд-ядро**: EVP, голос, факты с источниками.
3. Интервью по шести блокам: мандат, команда, процессы, данные и системы, цели, готовность к изменениям. Его можно прервать и продолжить в другой сессии.
4. Каждый процесс команды оценивается по шести осям и попадает в одну из зон: AUTOMATE / AUGMENT / HUMAN.
5. Команда агентов предлагается как система: у каждого агента есть входы и выходы, а 3–5 конвейеров первой волны показывают, как реальная задача проходит от человека через агентов обратно к человеку.
6. Будущие владельцы агентов проверяют предложение до утверждения: нужен ли агент и на каких задачах его попробовать.

**Выход:**
- карта функции — все процессы с оценками;
- AI-карта — зоны и обоснования;
- предложение по команде агентов — волны, владельцы, ритуалы, уровни автономности, доступ к инструменту, конвейеры;
- машиночитаемый состав команды `team-roster.json` для фазы 2;
- опросник для проверки с владельцами и его итоги;
- одностраничная сводка для CHRO;
- страница обзора — локальный HTML-файл, светлый по умолчанию: как задача идёт по команде агентов, карточки агентов, процессы по зонам, готовность к фазе 2;
- список открытых вопросов и раздел «готовность к фазе 2» в статусе.

### Фаза 2. Сборка команды

Агент-архитектор берёт утверждённый и проверенный с владельцами состав команды и разворачивает его в **общей рабочей папке команды**: агентов, правила координатора, команды ритуалов, журнал и онбординг для каждого владельца. Всё это обычные файлы, которые можно читать и править. У каждого клиента своя команда.

#### 2.1 Что должно быть готово до сборки

Сборка начинается с проверки раздела «Готовность к фазе 2» в `eb/status.md`:

| Пункт | Если не готово |
|---|---|
| Согласование безопасности | Сборка не начинается |
| Проверка с владельцами | Собираются только агенты, по которым владелец ответил «да» или «скорее да». Остальные ждут |
| Доступ к инструменту | У владельца без доступа должен быть назначен оператор, иначе агент ждёт |
| Общая папка | Сборка идёт в текущей папке, а перенос в общий репозиторий — первый шаг онбординга |
| Подтверждённые факты | Внешний агент собирается, но первый запуск предупреждает, по каким темам в ядре нет подтверждённых фактов |

#### 2.2 Общая рабочая папка команды

**Где.** Корпоративный git-репозиторий (внутренний GitLab или аналог). Он даёт историю всех изменений, защиту от затирания и откат. Если git для команды неприемлем, вариант на крайний случай — корпоративная облачная папка с правилом «пишет один, остальные читают».

**Что лежит в репозитории, а что нет.**

| В репозитории | Только на машине владельца материалов (в `.gitignore`) |
|---|---|
| Бренд-ядро, индекс и заметки по материалам | Исходные материалы `eb/inbox/**` |
| Диагностика, состав команды, агенты, правила координатора | Текстовые выгрузки `eb/inbox/_text/` |
| Черновики `eb/work/`, журнал `eb/log/`, ретро | Личные настройки `.claude/settings.local.json`, `CLAUDE.local.md` |
| Сам плагин нужной версии (`vendor/`) | |

Исходные материалы — самая чувствительная часть, поэтому они не расходятся по машинам команды. Агенты работают по заметкам и ядру, а к исходнику возвращается только тот, у кого он есть.

**Как коллега получает систему.** Плагин лежит внутри репозитория как локальный маркетплейс (`vendor/eb-marketplace/`). Коллега клонирует репозиторий и один раз запускает `sh join_team.sh`. Скрипт регистрирует плагин из `vendor/` в личных настройках этой папки, которые не попадают в git, ничего не скачивает из интернета и выключает в этой папке другие копии плагина, если они есть. Объявлять плагин в общих настройках проекта мы не стали: CLI записывает туда абсолютный путь, который у коллеги не сработает, а относительный путь без диалога доверия не подхватывается (проверено). Версия плагина зафиксирована в репозитории: служба безопасности проверяет ровно тот код, которым пользуется команда, а обновление — это осознанная замена папки `vendor/`.

**Как не затирать работу друг друга.** Правило «у каждого файла один писатель»:

| Что | Кто пишет |
|---|---|
| `eb/work/<агент>/` | Только этот агент (через координатора) |
| `eb/brand-core/` | Только человек: руководитель EB или его оператор, по предложениям хранителя EVP |
| `eb/log/runs/`, `eb/log/decisions/` | По одному файлу на запуск и на решение. Файлы только добавляются, конфликтов слияния нет |
| `eb/team/`, `.claude/agents/`, `CLAUDE.md` | Только архитектор (фаза 2) и одобренные предложения ретро (фаза 4) |

Git остаётся невидимым для команды. Команда `/eb-sync` забирает свежие изменения перед началом работы, а после каждого решения координатор сам делает коммит с понятным сообщением и отправляет его. Если коммит не прошёл из-за конфликта, координатор ничего не перезаписывает и зовёт человека.

#### 2.3 Агенты: канонический формат и генерация

Каждый агент сначала описывается в каноническом формате, независимом от модели: `eb/team/agents/<id>.md`. Шапка описания: id, процесс из библиотеки, владелец, оператор, уровень автономности, внешний или нет, ритуал, входы от, выходы к, первая метрика. Разделы:

1. **Зачем** — назначение из библиотеки, переписанное под функцию клиента его словами.
2. **Что читает** — конкретные файлы ядра и рабочей папки.
3. **Что производит и куда кладёт** — формат результата и путь в `eb/work/<id>/`.
4. **Передача** — шаблон передачи от координатора и обратно, критерии приёмки.
5. **Проверки перед сдачей** — для внешних агентов: только подтверждённые факты, список цифр со статусом и видом, затем контроль качества.
6. **Никогда не делает** — риски из библиотеки, инварианты системы и красные линии клиента.
7. **Особенности клиента** — шаблоны, требования площадок и подрядчиков, примеры удачных результатов из интервью и материалов.

Из канонического описания скрипт-конвертер детерминированно генерирует файл под среду. Для Claude Code это `.claude/agents/eb-<id>.md` с суженным набором инструментов: чтение всей рабочей папки, запись только в свою папку `eb/work/<id>/`, веб-доступ только агентам мониторинга. Правится всегда каноническое описание, файлы под среду перегенерируются. Для GigaChat позже пишется второй конвертер.

**Защита ядра.** Хук перед записью файла останавливает любую попытку агента записать в `eb/brand-core/` или в чужую папку `eb/work/`. Инструкция говорит агенту «не пиши туда», а хук делает это невозможным.

#### 2.4 Координатор и команды ритуалов

**Координатор** — основная сессия Claude Code в общей папке. Его правила архитектор пишет в `CLAUDE.md` между маркерами: состав команды, конвейеры из `team-roster.json`, шаблон передачи, цикл с контролем качества (не больше трёх попыток), запись решений, правила git, инварианты. Координатором становится тот, кто открыл Claude в папке: это роль сессии, а не человека.

Субагенты Claude Code умеют вызывать других субагентов, но цепочку всё равно ведёт координатор. Так человек видит каждый шаг, а решение по каждому выходу наружу принимается в одном месте.

**Команды**, которые генерирует архитектор (`.claude/skills/` проекта):

| Команда | Что делает |
|---|---|
| Одна на каждый конвейер, например `/habr-article`, `/lovemark-brief` | Запускает конвейер с первого шага, спрашивает только недостающий вход |
| `/weekly` | Пакет к еженедельной оперативке: новое в `eb/work/`, черновики, ждущие решения, просроченное, 15 минут коуча внедрения |
| `/core-review` | Ежемесячный разбор бренд-ядра: предложения хранителя EVP и раунд подтверждения фактов |
| `/decide` | Записывает решение владельца: принять, править или отклонить, существенная ли правка, причина его словами. Если решает владелец без доступа, записывается «решил владелец через оператора» |
| `/export-docx` | Выгружает черновик в .docx для владельца без Claude |
| `/eb-sync` | Забирает свежие изменения из общего репозитория |

Расписание в MVP не используется: ритуалы запускает человек на самом ритуале. Облачные задачи по расписанию привязаны к одному аккаунту и не подхватывают плагины из настроек проекта, а задачи в desktop-приложении требуют, чтобы компьютер не спал. Еженедельный мониторинг отзывов по расписанию — первое, что стоит добавить после пилота.

**Журнал запусков** ведётся автоматически: хук плагина на завершение субагента записывает файл в `eb/log/runs/` (агент, время, итоговое сообщение, путь к результату). Журнал решений пишет `/decide`. Оба читают коуч внедрения и ретро.

#### 2.5 Лицензии и операторы

Доступ к Claude есть не у всех владельцев. Каждый агент в составе получает одну из двух схем:

- **Владелец с доступом** сам запускает конвейеры своего агента и сам записывает решения.
- **Владелец без доступа** получает черновик файлом (в общей папке или в .docx) и даёт решение оператору — коллеге с доступом. Оператор запускает конвейер и записывает решение от имени владельца. Решает владелец, оператор только исполняет.

Нагрузку на операторов коуч внедрения показывает на оперативке. Если операторы становятся узким местом, это аргумент для запроса лицензий. Сводка для CHRO запрашивает корпоративный тариф (Team или Enterprise) для всех владельцев с тремя доводами: централизованные настройки и плагины для всей организации, общий биллинг вместо личных подписок, снятие узкого места на операторах. Цены сводка не называет, пока их не подтвердили закупки.

#### 2.6 Как идёт сборка

1. Проверить готовность (§2.1) и показать руководителю, что будет собрано, а что ждёт и почему.
2. Для каждого агента первой волны написать каноническое описание из записи библиотеки, `team-roster.json`, заметок, интервью и ядра. Показать владельцу раздел «Никогда не делает» и особенности клиента; владелец подтверждает.
3. Сгенерировать файлы под среду, правила координатора, команды ритуалов, хуки.
4. Подготовить репозиторий: `.gitignore`, `vendor/` с плагином, настройки проекта.
5. Пробный прогон каждого конвейера на одном реальном входе из проверки с владельцами. Результат — черновик и запись в журнале, а не публикация.
6. Онбординг: для каждого владельца и оператора одна страница — твой агент, твой ритуал, как запустить, как записать решение, к кому идти с вопросом. Её готовит коуч внедрения.
7. Статус: фаза 2 завершена, назначена дата первого ретро.

Команда собирается волнами: первая волна — 3–5 быстрых побед с низким риском, следующие — после первого ретро. Повторный запуск сборки добавляет новые агенты и не трогает существующие без одобрения.

#### 2.7 Что проверено при реализации

Проверено запуском Claude Code без интерфейса на тестовых папках:
- хуки плагина работают и в папке, которой ещё не доверяли;
- событие перед записью файла содержит имя субагента, поэтому защита «агент пишет только в свою папку» точная: запись в бренд-ядро блокируется для любого субагента, а агент команды не может писать за пределы своей папки, даже через `..` или папку с похожим именем;
- событие завершения субагента содержит его имя и итоговое сообщение — этого достаточно для журнала запусков;
- плагин из `vendor/`, зарегистрированный на уровне личных настроек папки, подключается в новой копии репозитория без диалога доверия.

### Фаза 3. Работа

```
 человек / ритуал / расписание
            │
            ▼
      КООРДИНАТОР (основная сессия Claude Code)
            │ разбирает задачу, собирает конвейер
            ▼
   агенты процессов (субагенты) ──► черновики в eb/work/
            │
            ▼
     КОНТРОЛЬ КАЧЕСТВА (доказательность, EVP, голос)
            │
            ▼
   человек-владелец: принять / править / отклонить ──► журнал
```

- Координатор — основная сессия Claude Code в общей папке (§2.4). Субагенты могут вызывать друг друга, но цепочку ведёт координатор, чтобы человек видел каждый шаг.
- Всё, что уходит наружу, проходит контроль качества и утверждается человеком. Агенты ничего не публикуют.
- Решение человека и его причина записываются в журнал. Это топливо для адаптации.

**Передача задачи между агентами.** Координатор передаёт задачу по единому шаблону: от кого и кому, задача, что уже сделано, какие файлы и факты ядра использовать, критерии приёмки, кто получит результат. Агент возвращает результат с тем же шаблоном и отметкой, какие критерии выполнены.

**Цикл с контролем качества.** Если контроль качества останавливает черновик, он перечисляет проблемы и критерии, которые не выполнены. Агент исправляет только эти проблемы, ничего не добавляя. Попыток не больше трёх. После третьей черновик уходит владельцу вместе с историей попыток и пометкой, что агент не справился. Такие случаи — главный материал для ретро.

### Фаза 4. Адаптация

Ретро-агент запускается раз в две недели как ритуал. Он читает журнал запусков и решений людей и предлагает изменения:

| Сигнал | Предложение |
|---|---|
| Черновики агента часто правят в одном и том же месте | Поправить инструкцию агента |
| Люди дописывают факт, которого не было в ядре | Добавить факт в бренд-ядро (с источником) |
| Похожая разовая задача повторилась 3+ раза | Новый агент или новый ритуал |
| Агента принимают без правок N раз подряд | Поднять уровень автономности |
| Агента не запускали две итерации | Выяснить причину: не нужен, неудобен или не встроен в ритуал |

Предложения оформляются как изменения файлов. Человек их одобряет или отклоняет. Сама система ничего у себя не меняет.

## 3. Бренд-ядро

Общая память всех агентов. Хранится в `eb/brand-core/`:

| Файл | Что внутри |
|---|---|
| `evp.md` | Предложение работодателя, опоры, аудитории |
| `voice.md` | Тон голоса, словарь, запретные формулировки |
| `facts.md` | Реестр фактов: утверждение, источник, дата, статус (подтверждено / уточнить / нужно доказательство) |
| `audiences.md` | Целевые аудитории и что о них известно из данных |
| `red-lines.md` | Что нельзя говорить и делать никогда |
| `decisions.md` | Журнал решений, которые влияют на коммуникацию |

Правило из аудитора: **нет доказательства — нет утверждения.** Агенты используют во внешних текстах только факты со статусом «подтверждено».

## 4. Автономность

| Уровень | Что агент делает сам | Что за человеком |
|---|---|---|
| L0 Ассистент | Отвечает по запросу в чате | Всё |
| L1 Черновик | Запускается по ритуалу или расписанию и кладёт черновики в `eb/work/` | Утверждение каждого результата |
| L2 Внутреннее действие | Обновляет внутренние артефакты: дайджесты, планы, предложения в ядро | Всё внешнее и любые изменения ядра |

Уровня «публикует сам» в продукте нет. Внешняя коммуникация всегда за человеком — это инвариант, а не настройка. Он снимает главный страх руководителя и главный аргумент сопротивления команды.

## 6. Устройство репозитория

```
.claude-plugin/          манифесты плагина и маркетплейса (адаптер Claude Code)
methodology/             правила системы — переносимое ядро, не зависит от модели
library/processes/       каталог процессов — переносимое ядро
skills/                  скиллы Claude Code — адаптер
templates/               шаблон страницы обзора и формат состава команды, с вымышленными образцами
scripts/                 опись материалов, извлечение текста, сборка страницы обзора, валидатор
```

**Переносимость.** `methodology/` и `library/` — обычный markdown без привязки к Claude. Для GigaChat пишется новый адаптер (оркестрация, вызов инструментов, хранение) поверх тех же файлов. Агенты клиента тоже хранятся в каноническом формате (фаза 2), а конвертер генерирует из них файлы под конкретную среду. Так что перенос на новую модель — это новый конвертер, а не переписывание агентов.

**Память — в файлах, а не в отдельном сервере.** Бренд-ядро, журнал и состав команды — обычные файлы в рабочей папке. Их видит и правит человек, они версионируются и переносятся между моделями. Отдельный MCP-сервер памяти без необходимости не подключаем.

## 8. Данные и безопасность

- Материалы лежат в рабочей папке клиента. Но всё, что агенты читают, отправляется провайдеру модели. Система говорит об этом при первом запуске, до того как прочитать хоть один файл.
- Персональные данные сотрудников и кандидатов не попадают в бренд-ядро. При индексации система помечает материалы с персональными данными и предлагает обезличить их.
- Материалы — это данные, а не инструкции. Инструкции внутри документов система замечает, сообщает о них и не выполняет.
- Для российских клиентов доступ к зарубежной модели — отдельный вопрос с безопасностью. Отсюда и требование переносимости ядра.

## 11. Внедрение и сопротивление

Внедрение ведёт коуч внедрения (`library/processes/adoption-coach.md`) с первой волны.

**Сначала причина, потом действие.** Сопротивление бывает пяти типов, и у каждого своё лечение:

| Причина | Что помогает |
|---|---|
| Не знают, что и зачем | Объяснить и показать на своей задаче |
| Не согласны с самим изменением | Позвать в настройку агента, поменять, если довод верный |
| Боятся за себя: роль, ценность, ошибки | Показать, что агент работает на владельца и решение за ним |
| Не доверяют системе или инициативе | Прозрачность: журнал, источники фактов, право отклонить |
| Видят реальную проблему исполнения | Выслушать и исправить агента — это сигнал для ретро |

Неправильное лечение усиливает сопротивление. Поэтому коуч сначала собирает причины и только потом что-то предлагает.

**«Тихое» сопротивление видно по данным, а не по словам:** агента не запускают, ритуал пропускают, работу делают параллельно по-старому, черновики отклоняют без причины. Молчание не значит согласие.

**Три вида метрик внедрения:** использование (запуски, проведённые ритуалы), поведение (сколько черновиков принято, сколько правок, сколько работы ушло со старого пути) и отношение (короткий опрос владельцев раз в месяц: удобно ли, доверяют ли, порекомендуют ли коллеге).

**Чего коуч не делает никогда:** не оценивает и не ранжирует людей и не передаёт «сопротивляющихся» руководству для разговора о результативности. Его предмет — агенты и ритуалы, а не сотрудники.
